## 찾아보고 알게 된 것
저장소 관계: 깃허브 저장소와 내 PC의 폴더는 명령어(Git)로 연결되어 코드를 백업하고 내려받는 '클라우드와 내 컴퓨터의 쌍둥이 저장소' 관계

• 내 PC의 폴더 (로컬 저장소, Local Repository): 내 컴퓨터에 직접 존재하는 폴더로, .git이라는 숨겨진 기록 파일이 포함되어 있어 실시간으로 코드를 수정하고 저장(커밋)하는 공간

• 깃허브의 저장소 (원격 저장소, Remote Repository): GitHub 같은 온라인 서버에 존재하는 저장소로, 내 컴퓨터의 작업 기록을 안전하게 백업하고 다른 사람과 공유하는 공간

원격 저장소의 이름: 내 PC에서 깃허브 저장소를 가리키는 기본 별명은 origin

### Git 커밋 메시지 규칙

커밋 메시지: 어떤 내용을 왜 바꿨는지 기록하는 설명. 앞머리에 변경 종류를 붙이면 커밋 목록에서 작업 내용을 쉽게 구분할 수 있음

기본 형식: `type(scope): 변경 요약`

- `type`: 변경 종류를 나타내는 영어 접두사
- `scope`: 변경한 영역. 구분이 필요할 때만 사용하며, 생략하면 `type: 변경 요약` 형태
- 변경 요약: 이 저장소에서는 짧고 구체적인 한국어로 작성

| 접두사 | 뜻 | 커밋 메시지 예시 |
| --- | --- | --- |
| `feat` | 새 기능이나 실습 코드 추가 | `feat(report): 일일 보안 보고서 생성 기능 추가` |
| `fix` | 잘못된 동작이나 오류 수정 | `fix(parser): 대문자 위험도 처리 오류 수정` |
| `docs` | 수업 노트, README 등 문서 변경 | `docs(git): 커밋 메시지 규칙 정리` |
| `refactor` | 동작은 유지하면서 코드 구조 정리 | `refactor(agent): 공통 설정 로딩 함수 분리` |
| `test` | 테스트 코드 추가 또는 수정 | `test(report): 위험도별 집계 검증 추가` |
| `chore` | 설정 변경과 저장소 유지 관리 | `chore(git): 가상환경 추적 제외` |

작성 기준: 파일 이름이나 확장자보다 변경 목적에 맞는 접두사를 선택. 노트북도 설명만 수정하면 `docs`, 새 기능을 추가하면 `feat`, 오류를 고치면 `fix` 사용

커밋 단위: 관련된 변경끼리 묶고, 서로 다른 목적의 작업은 가능한 한 별도 커밋으로 나누기. `modify`, `update files`처럼 내용이 모호한 메시지는 피하고, 자세한 이유가 필요하면 빈 줄 뒤 본문에 작성
