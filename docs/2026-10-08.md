## 찾아보고 알게 된 것

### 설정 분리와 하드코딩

하드코딩: 모델 이름이나 알림 주소처럼 바뀔 수 있는 값을 코드 안에 직접 적어 두는 것. 값을 바꿀 때마다 코드를 찾아 수정해야 하는 불편함이 있음

설정 분리: 바뀔 수 있는 값은 `config.json`에 모으고, 처리 방법은 코드에 두는 방식

| 설정 키 | 역할 |
| --- | --- |
| `model` | 사용할 LLM 모델 이름 |
| `approve_severity` | 어느 위험도부터 사람의 확인이 필요한지 정하는 기준 |
| `report_folder` | 보고서를 모아 둘 폴더 |
| `webhook_url` | 알림을 보낼 주소 |

- 비밀인 API 키는 `.env`에 보관하고 GitHub에 올리지 않기. 비밀이 아닌 설정은 `config.json`으로 관리
- `json.load(f)`는 JSON 파일을 읽고, `json.dump(config, f, ensure_ascii=False, indent=2)`는 한글과 들여쓰기를 유지하며 저장
- JSON은 문자열에 큰따옴표를 쓰고, `true`, `false`, `null`을 사용. 파이썬의 `True`, `False`, `None`과 표기가 다르며 주석은 넣을 수 없음
- `load_config`에서 필수 키를 확인하고, 빠진 키가 있으면 `None`을 반환해 파이프라인을 중단

### 위험도와 사람 확인 기준

위험도는 문자열 그대로 비교하면 사전 순서로 비교됨. `RANK = {"low": 1, "medium": 2, "high": 3}`처럼 숫자로 바꿔 기준 이상인지 `>=`로 판단

- `High`처럼 대문자가 섞이면 `.lower()`로 맞추기
- 알 수 없는 위험도는 `RANK.get(severity.lower(), 3)`으로 high 취급해 사람에게 확인받기
- 오전의 고정된 경보 목록에서는 승인 기준을 high에서 medium으로 바꾸자 확인 대상이 2건에서 4건으로 증가
- 오후 파이프라인 실습에서는 high 기준으로 1건, low 기준으로 6건이 출력됨. LLM의 위험도 판단은 실행마다 달라질 수 있음

### 웹훅 알림과 장애 허용

웹훅 알림: 정해진 주소로 HTTP 요청을 보내 처리 결과를 알리는 방식. 실습에서는 `requests.post(url, json={"text": message}, timeout=5)`로 알림 서버에 메시지를 보냄

장애 허용: 일부 기능에 문제가 생겨도 나머지 작업 결과를 유지하는 것. 보고서를 먼저 저장한 뒤 알림을 보내고, 연결 실패는 `try` / `except`로 처리

- `timeout`으로 네트워크 대기에 제한을 두고, 실패 시 `type(e).__name__`으로 오류 이름 확인
- 실패를 `pass`로 숨기지 않고 출력이나 로그로 남기기
- 꺼진 서버 주소를 넣은 `config_off.json` 실습에서 `[알림 실패] ConnectionError`가 출력돼도 보고서 파일은 남아 있는 것을 확인

### 파이프라인과 함수 사이의 값 전달

파이프라인: 여러 처리 단계를 정해진 순서로 연결한 것

오늘 만든 흐름: 설정 읽기 → 경보 파일 읽기 → LLM 요약 → 위험도순 정렬 → 총평과 보고서 생성 → 파일 저장 → 사람 확인 대상 집계 → 알림

- `print`는 화면에 보여 주고, `return`은 호출한 곳에 값을 전달. 함수가 값을 반환하지 않으면 호출 결과는 `None`
- 파일 이름과 요약 목록처럼 결과가 여러 개면 `{"filename": filename, "summaries": sorted_summaries}` 형태로 묶어 반환
- `if __name__ == "__main__":`을 사용하면 직접 실행할 때만 파이프라인이 동작하고, 다른 파일에서 `import`할 때는 자동 실행되지 않음
- 폴더는 `os.makedirs(folder, exist_ok=True)`로 만들고, 경로는 `os.path.join(folder, filename)`으로 연결

### 코드 리뷰와 단위 테스트

코드 리뷰: 실행 여부만 보지 않고 비밀 관리, 설정 분리, 응답 검증, 실패 처리, 기록의 다섯 항목으로 코드 확인

단위 테스트: 함수에 입력을 넣고 기대한 값이 나오는지 자동으로 확인하는 것. `assert 조건, "실패 메시지"`는 조건이 거짓이면 `AssertionError`로 멈춤

| 테스트한 함수 | 확인한 내용 |
| --- | --- |
| `make_lines` | 위험도 대문자 표시, 빈 목록 처리, 경보 한 건당 한 줄 |
| `needs_approval` | high 승인 필요, low 승인 불필요, 모르는 위험도도 승인 필요 |
| `parse_llm_json` | 코드 블록으로 감싼 JSON 처리, 일반 문장과 빈 문자열은 `None` 반환 |

노트북에서 함수별 3건씩 총 9건의 테스트 통과를 확인하고, `test_agent_core.py`에 모음. LLM을 실제로 호출하지 않고도 위 함수들의 동작을 검사할 수 있음

### 오류를 찾는 순서

| 오류 종류 | 실습 예시 | 확인 방법 |
| --- | --- | --- |
| 문법 오류 | `def` 뒤의 `:` 누락, 닫지 않은 괄호 | `SyntaxError`와 표시된 위치 확인 |
| 실행 오류 | 키 이름 오타로 생긴 `KeyError`, 전달받지 않은 날짜를 사용한 `NameError` | 트레이스백 마지막 줄부터 읽고 실제 오류가 난 함수 안의 줄 확인 |
| 논리 오류 | high 건수 누락, 잘못된 정렬 순서, 줄바꿈 누락 | 실제 값을 출력해 기대값과 비교하고 `assert`로 재확인 |

`High`, `HIGH`, `high `, ` high`를 같은 위험도로 세려면 `.strip().lower()`로 공백과 대소문자를 함께 정리. 조건의 `>`와 `>=`, 정렬 순서, `\n` 하나도 결과를 바꿀 수 있음
